# 架构方案

## 分层

Vue views/components -> Pinia stores -> api -> Tauri invoke -> Rust commands -> services -> domain/infra。
commands 验证调用来自本地 main WebView，远程账号页面不获得原生权限。

Tauri 2.12.3 的多 WebView 子视图依赖 unstable 特性，当前固定版本以控制 API 变更。
主窗口由本地 Vue 界面与多个原生子 WebView 构成，只有当前账号视图显示。
ResizeObserver 将内容区域坐标传给 Rust；打开弹窗前先隐藏原生视图。
原生创建在异步 command 中执行，避免 Windows 主线程等待 WebView 创建产生死锁。

## 账号流程

1. Rust 读取本地配置，不读取其他浏览器已有账号或 Cookie。
2. 为主账号创建独立 profile，打开原站登录地址。
3. Rust 后台每三秒同步同源顶层页面的已知登录缓存；每五分钟检查主账号权限和保活，前端不负责保活计时。
4. Rust 仅将 username、头像等展示数据返回 Vue，token 留在 Rust 调用期间的内存。
5. 搜索和代登录请求通过 Rust HTTP 客户端发送，身份始终取自主账号 WebView。
6. 每个子账号创建独立临时 profile；原页面加载完成后写入目标账号的完整登录数据，再导航到落地路径。
7. 登录注入消费一次性 payload；刷新、退出或重新打开网页不会重放登录 token。
8. 切换通过 hide/show 完成；关闭子账号销毁其 WebView。

## 数据与隔离

- settings.json：登录地址、接口地址、同源落地路径、记住开关、上次用户名。
- 主账号 profile：由操作系统 WebView 管理 Cookie、localStorage、IndexedDB。
- 子账号 profile：按随机 UUID 隔离、使用临时会话。
- Vue 状态和 workspace-changed 事件：只有显示信息和会话状态。
- 配置使用临时文件替换；不将 token 另存成 JSON。
- 本地 WebView 持久化数据受操作系统用户目录权限保护，不宣称应用额外提供了加密保险库。

保留主账号登录由系统 WebView 缓存实现，退出登录时可以清除该 profile 的浏览数据。
主账号过期后锁定子账号；重新登录为不同身份/租户时关闭旧子账号。
新 token 必须重新校验权限；授权缓存只绑定本次 token 和租户的指纹，且不持久化。
每次检索、添加和子账号重登都实时重新校验权限；所有异步结果使用前再次核对主账号凭据，拒绝过期响应。
保活由 Rust 任务驱动，不受窗口最小化的前端定时器节流影响；系统休眠/断网期间不保证请求准时到达。
子账号在切换时及当前显示期间每五分钟向服务端验证，三秒本地同步另行识别缓存/JWT 过期。
重新登录在同一个独立子 WebView 内重新排入一次性 payload，消费后清空，不会在刷新/退出时重放。
持久化 profile 以完整系统登录地址派生，避免切换系统时沿用另一系统的缓存。

## 错误与一致性

写操作由 tokio Mutex 串行化，避免多次确认生成重复会话。
检索使用请求序号丢弃过期结果；列表有加载、错误、空结果与分页状态。
账号选择后再次验证主账号 token 未发生变化，再创建子视图。
HTTP 客户端禁用自动重定向，避免认证请求被转发至未配置目的地；不关闭 TLS 验证。
读取/注入脚本校验 origin 和顶层页面；导航只接受 HTTP(S)。

## 维护

只把国内大型开源管理端常见的目录和分层习惯应用于此项目，不复制整个后台系统。
当前采用单仓库单客户端，未来第二套业务协议可以在 infra 下新增独立适配模块。
新增架构或平台的可运行性需要 WebView 实测，不能只凭 Rust target 认定完成。
